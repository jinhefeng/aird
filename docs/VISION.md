# 下一代 AI 驱动文档协作平台 (Aird) 愿景

## 核心理念
传统的文档管理平台（如 Confluence, Notion）主要面向“人与人”的协作，而下一代平台应当面向“人与 AI”以及“AI 与 AI”的协作。在 AI 驱动的开发模式下，文档不再仅仅是静态的文本，而是**可计算、可执行、可溯源的动态契约**。

## 为什么 AI 时代的文档平台不一样？

1. **从静态描述到动态契约 (Living Documents)**
   - 传统文档：写完即过时。代码变更后，文档很少同步更新。
   - AI 文档：文档与代码库深度绑定。当产品需求 (PRD) 发生改变时，AI 能够自动评估对现有代码和测试用例的影响；反之，代码更新也能反向同步更新 API 文档和架构图。

2. **多智能体协作中枢 (Multi-Agent Hub)**
   - 文档平台应当是不同角色 AI Agent 的工作台：
     - **产品 Agent**：协助完善 PRD，补充边缘场景。
     - **架构 Agent**：根据 PRD 自动生成系统设计、数据库 Schema 和 API 接口。
     - **测试 Agent**：基于需求文档自动生成测试用例（BDD/TDD）。
     - **开发 Agent**：根据契约直接生成代码骨架甚至具体实现。

3. **上下文极度富集 (Context-Rich)**
   - AI 需要大量的上下文才能写出好代码。文档平台应当自动构建需求、设计、代码、测试、Issue 之间的拓扑知识图谱 (Knowledge Graph)，为 AI 编码助手提供最精准的 Context。

4. **可执行的文档 (Executable Docs)**
   - 文档中的 API 定义可以直接发起请求（类似 Postman）。
   - 文档中的数据模型可以直接生成并在沙箱中初始化数据库表。

## 讨论方向建议

为了进一步细化，我们可以从以下几个维度展开讨论：

1. **核心场景与痛点**：目前在利用 AI 辅助开发时，遇到最大的文档管理痛点是什么？（例如：AI 找不到最新的 API，或者 PRD 里的边缘情况 AI 注意不到）
2. **产品形态**：它是一个类似 Notion 的纯 Web 应用，还是深度集成在 IDE（如 VSCode）和代码仓库（如 GitHub/GitLab）中的插件？
3. **关键数据模型**：如何定义一篇“AI 可读”的文档？我们需要一套新的结构化标记语言（比如基于 Markdown 扩展的 MDX 或更严格的 Schema）吗？
